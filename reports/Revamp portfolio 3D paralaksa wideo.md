# Zbuduj jeden sygnałowy ruch zamiast dziesięciu efektów

Portfolio na poziomie Awwwards w latach 2024-2026 wygrywa dyscypliną, a nie liczbą efektów: zwycięzcy to niemal wyłącznie strony dwukolorowe (czerń plus biel albo czerń plus jeden akcent), które cały "efekt wow" wkładają w jeden spójny system ruchu, najczęściej przejścia stron niosące wideo albo jedną scenę WebGL, i zdobywają Developer Award na ocenach animacji (8,4-9,0), przy dostępności jako najsłabszej ocenie (6,2-7,0). Dla Piotra Jeleniewicza oznacza to rewizję przez odejmowanie i ujednolicenie: ciemna baza z jednym akcentem (kolor śladu oscyloskopu), jeden model 3D fizycznego obiektu z jego świata (antena radioteleskopu SeeSky albo płytka FPGA) prowadzony scrollem w stylu Oryzo, krótkie wyciszone klipy projektów w miejsce kręconych kółkiem galerii zrzutów oraz modal wideo w miejsce lightboxa. Technicznie najlepiej pasuje vanilla Three.js ładowany leniwie przez importmap (bez bundlera, GitHub Pages zostaje), GSAP ScrollTrigger zsynchronizowany z Lenisem na jednym tickerze, modele GLB kompresowane przez `gltf-transform` z Meshopt, oraz wideo AV1 WebM plus H.264 MP4 trzymane wprost w repo. Nisza jest wolna: nie znaleziono żadnego nagrodzonego w latach 2024-2026 portfolio inżyniera elektroniki, więc istniejący separator oscyloskopu z szeregiem Fouriera już teraz jest bardziej specyficznym motywem niż cokolwiek u zwycięzców. Ze skilli agentowych warto zainstalować przede wszystkim oficjalny `greensock/gsap-skills`, potem `CloudAI-X/threejs-skills` i `heygen-com/hyperframes` do rolek wideo.

Jeden pomiar blogowy dał 462 KB dla małego przykładu w vanilla Three.js wobec 1035 KB w R3F ([svilenkovic.com](https://svilenkovic.com/3d/three-js-vs-react-three-fiber)); metoda nie jest opisana, ale kierunek jest jasny. Sam runtime Spline'a jest większy niż three, gsap i lenis razem. Warto też odnotować, że **GSAP jest w całości darmowy, łącznie z dawnymi wtyczkami Club (ScrollTrigger, SplitText, MorphSVG, ScrollSmoother), także komercyjnie**, a instrukcje o prywatnym rejestrze `npm.greensock.com` są nieaktualne ([README GSAP 3.15.0](https://cdn.jsdelivr.net/npm/gsap@3.15.0/README.md)).

Integracja bez bundlera wygląda tak (szkic złożony z API GSAP i Lenisa, nie skopiowany z jednego źródła). Three.js ładuje się dynamicznym `import()` dopiero, gdy sekcja zbliża się do viewportu, dokładnie w duchu istniejącego `near(el)` w `js/effects.js`:

```html
<script type="importmap">
{ "imports": {
  "three": "https://cdn.jsdelivr.net/npm/three@0.186.1/build/three.module.js",
  "three/addons/": "https://cdn.jsdelivr.net/npm/three@0.186.1/examples/jsm/"
} }
</script>
```

```js
import * as THREE from 'three';
import { GLTFLoader } from 'three/addons/loaders/GLTFLoader.js';
import { MeshoptDecoder } from 'three/addons/libs/meshopt_decoder.module.js';
const renderer = new THREE.WebGLRenderer({ canvas, antialias: true, alpha: true });
renderer.setPixelRatio(Math.min(devicePixelRatio, 2));
const loader = new GLTFLoader().setMeshoptDecoder(MeshoptDecoder);
const { scene: board } = await loader.loadAsync('models/basys3.glb');
scene.add(board);
gsap.timeline({ scrollTrigger: { trigger: '#hero3d', start: 'top top', end: '+=150%', pin: true, scrub: 1 } })
  .to(board.rotation, { y: Math.PI * 1.25, ease: 'none' }, 0)
  .to(camera.position, { z: 3, y: 0.4, ease: 'none' }, 0);
gsap.ticker.add(() => { if (visible) { camera.lookAt(0, 0, 0); renderer.render(scene, camera); } });
```

Pipeline modeli opiera się na `gltf-transform`. W obecnych wersjach domyślne ustawienia `optimize` to już **`--compress meshopt`, `--texture-compress auto`, `--texture-size 2048`**, plus simplify, weld, join, palette, prune i dedup ([cli.ts](https://raw.githubusercontent.com/donmccurdy/glTF-Transform/main/packages/cli/src/cli.ts); [gltf-transform.dev](https://gltf-transform.dev/cli)). Meshopt jest lepszym wyborem niż Draco dla modelu hero: to domyślna opcja narzędzia, obejmuje też animacje i morph targets, których Draco nie kompresuje ([svilenkovic.com](https://svilenkovic.com/3d/meshopt-compression)), a jego zysk nie zależy od tego, czy serwer gzipuje `.glb`, co nie jest pewne ([A-Frame docs](https://aframe.io/docs/1.6.0/components/gltf-model.html)). KTX2 opłaca się, gdy liczy się pamięć GPU, bo tekstury KTX zostają skompresowane w GPU, a większość formatów glTF trzeba w całości rozpakować ([Khronos KTX Artist Guide](https://github.com/KhronosGroup/3D-Formats-Guidelines/blob/main/KTXArtistGuide.md)); ETC1S nadaje się do koloru, UASTC do normal map ([Khronos](https://khronos.org/ktx/)).

```bash
npm i -g @gltf-transform/cli
gltf-transform inspect board.glb
# wariant najprostszy: tekstury WebP, klient nie potrzebuje transkodera KTX2
gltf-transform optimize board.glb board.opt.glb --compress meshopt --texture-compress webp --texture-size 1024
# wariant oszczędzający pamięć GPU (wymaga KTX-Software na PATH)
gltf-transform optimize board.glb board.opt.glb --compress meshopt --texture-compress ktx2 --texture-size 1024
```

Jako budżet przyjąłbym (to reguła kciuka, nie liczba z oficjalnego źródła) 0,5-2 MB na model hero, 50-150 tys. trójkątów i tekstury do 1024 px; płytka z KiCada ze wszystkimi elementami łatwo przekracza milion trójkątów przed simplify, więc `--simplify` nie jest opcjonalne.

Modele elektroniki mają trzy realne źródła. Własne PCB: **KiCad 9+ eksportuje GLB natywnie** (GUI File > Export albo `kicad-cli pcb export glb` z flagami typu `--subst-models` i `--include-tracks`) ([KiBot](https://kibot.readthedocs.io/en/latest/configuration/outputs/export_3d.html); [KiCad 10 CLI](https://docs.kicad.org/10.0/en/cli/cli.pdf)), ale zgłoszono, że eksport z obrazu Docker CLI gubił kolory, które GUI zachowywał ([kicad-cli-docker #8](https://gitlab.com/kicad/packaging/kicad-cli-docker/-/issues/8)). Ładniejsze materiały (połysk soldermaski, miedź, sitodruk) daje **pcb2blender**: wtyczka z PCM KiCada eksportuje `.pcb3d`, Blender importuje go przez File > Import > PCB ([pcb2blender](https://github.com/30350n/pcb2blender)), a potem trzeba zbake'ować proceduralne materiały do tekstur, bo eksporter glTF nie przenosi węzłów proceduralnych. Basys 3: **Digilent udostępnia oficjalny plik STEP w sekcji "Additional Resources" na dole strony Resource Center** i nie współpracuje z żadnym zewnętrznym hostingiem modeli ([forum Digilent](https://forum.digilent.com/topic/23889-3d-models-of-boards/); [Basys 3 Resource Center](https://digilent.com/reference/programmable-logic/basys-3/start)); licencja pliku nie jest nigdzie jasno opisana, więc warto ją sprawdzić przed publikacją. Antena radioteleskopu: najczyściej zbudować ją proceduralnie w Three.js (`LatheGeometry` z profilu paraboli plus trójnóg feedu), co eliminuje kwestie licencyjne i daje kilkadziesiąt linii kodu zamiast pliku. Alternatywą jest Sketchfab, gdzie każdy model ma licencję Standard (pozwala na wszystko, łącznie z komercją) albo Creative Commons; wszystko poza CC0 wymaga uznania autorstwa, a NC zabrania użycia komercyjnego ([Sketchfab Help](https://help.sketchfab.com/en/articles/16152217)).

Rekomendacja kompozycyjna: jedna antena SeeSky jako obiekt "dolly" na scrollu w sekcji o radioteleskopie albo w hero, a reszta strony w czystym HTML. To przywraca talerz, który usunięto wcześniej jako płaski efekt canvas, ale w formie jednego modelu zamiast kolejnej warstwy dekoracji.

## Lenis i ScrollTrigger muszą chodzić na jednym tickerze

Oficjalna konfiguracja z README Lenisa 1.3.26 sprowadza się do trzech linii: **`lenis.on('scroll', ScrollTrigger.update)`, `gsap.ticker.add((time) => lenis.raf(time * 1000))` i `gsap.ticker.lagSmoothing(0)`**, plus dołączenie `lenis/dist/lenis.css` ([Lenis README](https://cdn.jsdelivr.net/gh/darkroomengineering/lenis@1.3.26/README.md)). Mnożenie przez 1000 wynika z tego, że GSAP podaje sekundy, a Lenis oczekuje milisekund. Domyślne opcje to `lerp` 0,1, `smoothWheel` true, `autoRaf` false, `respectReducedMotion` true i `anchors` false, czyli linki kotwic są blokowane, dopóki się ich nie włączy. Ograniczenia: brak wsparcia dla CSS scroll-snap, Safari limitowane do 60 fps (30 fps w trybie niskiego poboru), gładkie przewijanie zatrzymuje się nad iframe'ami.

Obecne repo łamie tę konfigurację w trzech miejscach, co zweryfikowałem w kodzie. `js/main.js` tworzy `new Lenis()` (linia 508) i napędza go własną pętlą `requestAnimationFrame` (linie 511-513), bez `ScrollTrigger.update` i bez integracji z tickerem. `css/style.css` w linii 28 ustawia `scroll-behavior: smooth` na `body`, a nadpisanie `.lenis.lenis-smooth { scroll-behavior: auto !important; }` (linia 3007) trafia tylko w element `html`. `js/effects.js` ma do tego osobną pętlę rAF. Oficjalna lista typowych błędów GSAP mówi wprost, że **CSS `scroll-behavior: smooth` psuje pomiary przy refresh**, że ScrollTrigger należy umieszczać na timeline-rodzicu zamiast w zagnieżdżonych tweenach, tworzyć triggery w kolejności strony przy pinowaniu, używać wartości funkcyjnych z `invalidateOnRefresh: true` i wołać `ScrollTrigger.refresh()` po załadowaniu obrazów ([GSAP: common ScrollTrigger mistakes](https://gsap.com/resources/st-mistakes/)). Połączenie braku `ScrollTrigger.update`, `scroll-behavior: smooth` i przesuwającego layout paddingu `bg-window` jest prawdopodobnym wyjaśnieniem opisanego w CLAUDE.md problemu, w którym reveal-e `data-animation` w `#projects`/`#online` nigdy nie odpalały. To hipoteza do przetestowania, nie potwierdzona diagnoza, ale naprawa i tak jest warunkiem wstępnym dla każdego scrubowanego efektu 3D:

```js
// zamiennik lenisScrollAnimation() w js/main.js (komentarze po polsku, zgodnie z konwencją)
gsap.registerPlugin(ScrollTrigger);
const lenis = new Lenis({ lerp: 0.1, anchors: true });   // autoRaf zostaje false
lenis.on('scroll', ScrollTrigger.update);
gsap.ticker.add((t) => lenis.raf(t * 1000));
gsap.ticker.lagSmoothing(0);
window.addEventListener('load', () => ScrollTrigger.refresh()); // po obrazach i fontach
```

Potem warto przenieść ciało pętli z `effects.js` do `gsap.ticker.add(...)`, żeby cała strona miała jeden zegar; reguła "nowe efekty dołączają do jednej pętli" zostaje zachowana, tylko pętlą staje się ticker GSAP. `anchors: true` może zastąpić własny handler `a[href^="#"]` w main.js. Przy scrubie lepiej dać `scrub: 0.5`-`1` niż `scrub: true`, bo Lenis już wygładza, animować tylko `transform` i `opacity`, a pin i scrub wyłączać przez `gsap.matchMedia()` z `prefers-reduced-motion`.

Natywny CSS przejmuje teraz lżejszą część pracy. **Scroll-driven animations (`animation-timeline: scroll()/view()`, `animation-range`, `view-timeline`) działają w Chrome/Edge 115+, Safari 26+ i Firefox 159, który trafia do wersji stabilnej 27.10.2026**, trzy dni po dacie tego raportu ([MDN browser-compat-data v8.1.7](https://unpkg.com/@mdn/browser-compat-data/data.json)). Wcześniejsze strony twierdzące, że Firefox wydał to w wersji 126 lub 132, są błędne. Firefox 159 był w danych BCD jeszcze w becie, więc wersję warto potwierdzić w [notatkach wydania Firefox 159](https://developer.mozilla.org/docs/Mozilla/Firefox/Releases/159). Bezpieczny wzorzec to stan końcowy jako domyślny i animacja w `@supports` ([cssawwwards](https://cssawwwards.com/blog/css-scroll-driven-animations-guide-2026)), co pozwala zastąpić IntersectionObserver w `.fx-reveal` czystym CSS:

```css
@supports (animation-timeline: view()) {
  .fx-reveal { animation: reveal linear both; animation-timeline: view(); animation-range: entry 0% cover 30%; }
}
@keyframes reveal { from { opacity: 0; transform: translateY(40px); } }
```

Podział ról jest więc jasny: CSS dla prostych reveal-i i delikatnej paralaksy, GSAP dla pinowania, scrubowanej kamery 3D i wszystkiego, co steruje canvasem. View Transitions w wersji same-document (`document.startViewTransition`) to już Baseline: Chrome 111, Safari 18, Firefox 144. Wersja cross-document (`@view-transition { navigation: auto; }`) działa w Chrome/Edge 126+ i Safari 18.2+, ale **nie w Firefoksie** (bug 1860854) ([MDN BCD](https://unpkg.com/@mdn/browser-compat-data/data.json)); przeglądarki bez wsparcia po prostu ładują stronę normalnie ([CSS-Tricks](https://css-tricks.com/cross-document-view-transitions-part-1/)). Dla jednostronicowego portfolio najprostszy zysk to `startViewTransition()` przy otwieraniu modalu wideo i przełączaniu galerii. Jeśli projekty dostaną własne podstrony (wzorzec Landberga "home -> projekt"), wystarczy `@view-transition` w CSS każdej strony i wspólne `view-transition-name` na miniaturze projektu, bez żadnego routera i bez ryzyka na GitHub Pages.

## Wideo projektów to AV1 plus H.264 w repo, a scrub to sekwencja klatek

U zwycięzców wideo żyje w przejściach i modalach, nie w luźnych embedach: Landberg niesie wideo przez przejścia i modal profilu ([Awwwards](https://www.awwwards.com/sites/jesper-landberg-4)), Mangham ma modal z przejściem po projekcie ([Awwwards](https://www.awwwards.com/sites/elliott-mangham)). Dla tej strony naturalny ruch to zastąpienie lub uzupełnienie galerii zrzutów `#gal-jobagg`/`#gal-passmgr` 5-10-sekundowymi wyciszonymi pętlami prawdziwego UI LabInc, Job Aggregatora i Password Managera w istniejącym boksie `.tf__project_hero`, a `#fx-lightbox` zamienić w modal z pełną rolką.

Recepta kodowania: dwa lub trzy pliki w kolejności `<source>` od najlepszego kodeka, bo **przeglądarka bierze pierwsze źródło, które obsługuje, a nie najmniejsze** ([web.dev](https://web.dev/articles/replace-gifs-with-videos)). Ten sam artykuł pokazuje skalę zysku: GIF 3,7 MB, MP4 551 KB, WebM 341 KB. Sprzętowe dekodowanie AV1 pojawiło się u Apple dopiero w iPhonie 15 Pro, M3 i M4 iPad Pro, a Safari wystawia AV1 tylko na takich urządzeniach, więc starsze iPhone'y i Maki M1/M2 spadają do następnego źródła ([Bitmovin](https://bitmovin.com/apple-av1-support)). libsvtav1 ma zakres CRF 0-63 i różne domyślne wartości w różnych rewizjach wiki ffmpeg, więc CRF trzeba ustawiać jawnie ([ffmpeg trac Encode/AV1](https://trac.ffmpeg.org/wiki/Encode/AV1?version=52)); CRF 35 przy presecie 6 to społecznościowy, nieoficjalny punkt startowy ([lista Cinelerra](https://lists.cinelerra-gg.org/pipermail/cin/2024-September/008651.html)). Konkretne wartości poniżej to moja synteza, do strojenia na oko, bo tekst UI szybko się rozmywa (web.dev-owe CRF 41 dla VP9 jest dla zrzutów ekranu za agresywne):

```bash
VF="scale='min(1280,iw)':-2:flags=lanczos,fps=30"
# 1) AV1 w WebM
ffmpeg -i rec.mov -vf "$VF" -an -c:v libsvtav1 -preset 6 -crf 35 -g 60 -pix_fmt yuv420p -svtav1-params tune=0 out.av1.webm
# 2) H.264 MP4 jako uniwersalny fallback
ffmpeg -i rec.mov -vf "$VF" -an -c:v libx264 -preset slow -crf 23 -profile:v high -pix_fmt yuv420p -g 60 -movflags +faststart out.mp4
# 3) poster z pierwszej klatki, potem konwersja do WebP/AVIF
ffmpeg -i out.mp4 -frames:v 1 -q:v 2 poster.png
```

```html
<video autoplay muted loop playsinline preload="none" poster="poster.webp" width="1280" height="720">
  <source src="out.av1.webm" type='video/webm; codecs="av01.0.05M.08"'>
  <source src="out.mp4" type='video/mp4; codecs="avc1.640028"'>
</video>
```

`-an` ma znaczenie poza rozmiarem: zgodnie z polityką WebKit wideo bez ścieżki audio odtwarza się automatycznie, a `playsinline` jest wymagane na iPhonie, żeby nie przechodzić w pełny ekran ([WebKit](https://webkit.org/blog/6784/new-video-policies-for-ios/)). Parametr `codecs=` przy źródle AV1 pozwala Safari na sprzęcie bez AV1 pominąć ten plik. `-movflags +faststart` przenosi atom moov na początek, by odtwarzanie ruszyło przed pobraniem całości ([skillselion](https://skillselion.com/skills/josiahsiegel/claude-plugin-marketplace/ffmpeg-fundamentals-2025)). Nagrania najprościej robić skryptem Playwright z `recordVideo`, bo Playwright jest już na maszynie Piotra; tytułowane rolki można złożyć w HyperFrames, który renderuje kompozycje HTML/GSAP do MP4 w headless Chrome przez FFmpeg ([heygen-com/hyperframes](https://github.com/heygen-com/hyperframes)), czyli w tym samym języku co strona.

Hosting nie wymaga niczego poza repo. Limity GitHub Pages to **1 GB opublikowanej strony, 100 GB/miesiąc miękkiego limitu transferu i 10 minut na deploy** ([GitHub Docs: Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)), a git ostrzega powyżej 50 MiB i blokuje powyżej 100 MiB na plik ([GitHub Docs: large files](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)). Git LFS nie jest dokumentowany jako serwowany przez Pages, a na innych platformach daje pliki-wskaźniki zamiast treści ([cloud.gov Pages](https://cloud.gov/pages/documentation/large-file-handling)), więc nie warto go używać. Trzy rolki i podglądy po 0,3-2 MB to razem kilka megabajtów; przy 5 MB wideo na pełną wizytę limit 100 GB to ok. 20 tys. wizyt miesięcznie, czyli daleko ponad ruch portfolio. Ponieważ wszystko w repo idzie na produkcję, surowe `.mov` trzeba trzymać w `.gitignore`. Gdyby wideo urosło, sensowne są **Cloudflare R2 (zerowy egress, darmowe 10 GB-miesiąc)** ([Filebase](https://filebase.com/blog/cloudflare-r2-pricing-costs-savings-and-alternatives-in-2026/)), Bunny Stream (od 0,01 USD/GB przechowywania, minimum 1 USD/mies.) ([bunny.net](https://bunny.net/pricing/stream/)) albo Cloudflare Stream (5 USD za 1000 minut przechowywanych, 1 USD za 1000 minut dostarczonych) ([Cloudflare](https://developers.cloudflare.com/stream/pricing/index.md)). Długie, narrowane demo lepiej dać na YouTube za fasadą `lite-youtube-embed` (ok. 3 KB, iframe dopiero po kliknięciu), co w jednym zbiorze danych skróciło średnie LCP o ok. 800 ms ([corewebvitals.io](https://corewebvitals.io/pagespeed/perfect-youtube-core-web-vitals)).

Wideo scrubowane scrollem ma trzy techniki. **`video.currentTime` jest najlżejsze, ale asynchroniczne seekowanie z lukami między klatkami kluczowymi powoduje przycięcia**, co opisuje deweloper, który przeniósł swoje portfolio z `<video>` na canvas z klatkami ([DEV](https://dev.to/pratham7711/how-i-made-a-scroll-scrubbed-video-portfolio-fast-nextjs-15-gsap-canvas-1mj6)); dyskusje CSS WG potwierdzają, że nie ma natywnego mechanizmu "scroll timeline steruje wideo" ([W3C, wrzesień 2024](https://lists.w3.org/Archives/Public/public-css-archive/2024Sep/0784.html)). Sekwencja obrazów na `<canvas>` jest najbardziej niezawodna i dokładna co do klatki, kosztem transferu. WebCodecs daje bezpośredni dostęp do klatek w obu kierunkach, ale materiałów produkcyjnych jest mało ([Medium](https://lionkeng.medium.com/a-tutorial-webcodecs-video-scroll-synchronization-8b251e1a1708)), a README `scrolly-video` twierdzi, że to tylko Chrome ([npm](https://www.npmjs.com/package/scrolly-video)), co jest prawdopodobnie nieaktualne i wymaga sprawdzenia na caniuse. Dla strony bez bundlera z istniejącym wzorcem `fx-host`/`fx-bg`/`near(el)` wygrywa sekwencja klatek: najpierw co czwarta klatka w niskiej rozdzielczości, potem uzupełnienie, `createImageBitmap()`, rysowanie tylko blisko viewportu i jedna statyczna klatka przy reduced motion. 90 klatek WebP po 40-80 KB to szacunkowo 3,5-7 MB, więc na telefonach lepiej pokazać zwykłą pętlę lub kadr. Jeśli już `currentTime`, to z kodowaniem all-intra (`-g 1 -keyint_min 1 -sc_threshold 0`) i tylko jednym seekiem w locie naraz.

## Mobilny budżet i WCAG 2.2.2 rozstrzygają, czy efekty pomagają

Progi Core Web Vitals w 2026 się nie zmieniły: **LCP do 2,5 s, INP do 200 ms, CLS do 0,1 na 75. percentylu**, osobno dla mobile i desktopu; INP zastąpił FID w 2024, więc porady oparte na FID są nieaktualne ([web.dev](https://web.dev/articles/vitals)). Najczęściej cytowany budżet bajtowy, Alexa Russella, celuje w urządzenia P75 i daje **ok. 1,3 MiB całości ścieżki krytycznej dla strony opartej o JS przy 5 s pierwszego ładowania** oraz ok. 300-350 KiB JS po gzip w edycji 2023, z JS co najmniej trzy razy droższym bajt w bajt niż HTML, CSS czy obrazy na słabym sprzęcie ([infrequently.org 2024](https://www.infrequently.org/page/2/); [baseline 2023](https://infrequently.org/2022/12/performance-baseline-2023?ref=refind)). Skoro sam Three.js to 185 KB gzip, 3D i wideo muszą być ładunkami po LCP, poza budżetem krytycznym.

Ciężkie strony trzymają LCP poniżej 2,5 s, bo element LCP jest tani. Od Chrome 116 `<video>` może być kandydatem LCP, mierzonym na pierwszej wyświetlonej klatce ([Chromium changelog](https://chromium.googlesource.com/chromium/src/+/main/docs/speed/metrics_changelog/2023_08_lcp.md)). LCP zapisuje się przy posterze lub pierwszej klatce, co nastąpi wcześniej, więc szybki poster "zamyka" wynik; Chrome nie obsługuje preloadu samego wideo, więc preloaduje się poster przez `<link rel="preload" as="image" fetchpriority="high">`. W demie DebugBear LCP spadło z 1,55 s do 1,23 s z posterem i do 1,2 s z preloadem posteru ([DebugBear](https://www.debugbear.com/blog/optimize-video-lcp)). Wzorzec web.dev dla wideo bez autoplay to `preload="none"` plus poster; dla autoplay źródła w `data-src` podmieniane przez IntersectionObserver ([web.dev](https://web.dev/articles/lazy-loading-video)). Na tej stronie LCP powinien zostać nagłówek i tekst intro w bannerze; canvas WebGL ani wideo nie mogą być największym elementem nad zgięciem.

W Three.js największą dźwignią jest pixel ratio: **`renderer.setPixelRatio(Math.min(devicePixelRatio, 2))`**, bo ekrany DPR 2-3 renderują 4-9 razy więcej pikseli, a na słabych urządzeniach można zejść do 1; render na żądanie (tylko gdy scena się zmieniła) zbija zużycie GPU w spoczynku prawie do zera ([hontran.dev](https://www.hontran.dev/blog/three-js-performance-optimization); [forum three.js](https://discourse.threejs.org/t/searching-ways-for-flexible-performance-improvement-on-weak-devices/2439)). `detect-gpu` może dobrać jakość przed załadowaniem 3D, ale jego baza nie zna nowych GPU, a laptopy z grafiką zintegrowaną bywają słabsze od telefonów, więc "czy mobile" to zły wskaźnik. `hardwareConcurrency` Safari przycina do 4 lub 8 ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/hardwareConcurrency)), a `deviceMemory` jest tylko w Chromium. Proponowany budżet dla średniej klasy Androida na 4G to synteza, nie oficjalna tabela:

| Pozycja | Budżet | Uwagi |
|---|---|---|
| LCP (P75 mobile) | do 2,5 s, w labie cel 2,0 s na Slow 4G | Tekst albo mały poster, nigdy canvas czy wideo |
| INP | do 200 ms | Praca rAF poniżej ok. 8-10 ms na klatkę, dekodery GLB poza wątkiem głównym |
| CLS | do 0,1 | `width`/`height` lub `aspect-ratio` na każdym `<video>`, canvasie i galerii |
| JS krytyczny (gzip) | ok. 150-350 KiB | Three.js przez dynamiczny `import()` po LCP |
| Pierwsze ładowanie przed scrollem | ok. 1-1,5 MB | Zgodne z 1,3 MiB Russella |
| Model GLB | 1-2 MB mobile, 3-5 MB desktop | Reguła kciuka |
| Podgląd po hover | 300-800 KB, 3-6 s, do 720 px | Ładowany dopiero na intencję |
| Rolka po kliknięciu | dowolnie, `preload="none"` | Poza budżetem startowym |

Heurystyka tierowania: `prefers-reduced-motion`, `navigator.connection?.saveData`, `deviceMemory <= 4`, `hardwareConcurrency <= 4` lub niski tier z detect-gpu oznaczają postery zamiast WebGL, a strażnik FPS (mediana klatki powyżej ok. 25 ms przez 2 s) najpierw obniża DPR do 1, potem przełącza na statyczny obraz. Wideo trzeba pauzować poza viewportem własnym IntersectionObserverem, bo automatycznie robi to tylko iOS, a wszystko zatrzymywać na `visibilitychange`.

Dostępność to obszar, na którym zwycięzcy wypadają najsłabiej, więc tu najłatwiej się wyróżnić. **WCAG 2.2 SC 2.2.2 (poziom A) wymaga mechanizmu pauzy, zatrzymania lub ukrycia dla ruchomej treści, która startuje automatycznie, trwa ponad 5 s i jest pokazywana równolegle z inną treścią**, a "startuje automatycznie" obejmuje też start po focusie, hover albo wjechaniu w viewport przy scrollu ([W3C Understanding 2.2.2](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)). Pętle w tle, kanwy paralaksy i scena 3D podlegają więc tej regule. Praktyczne rozwiązanie to jeden globalny przełącznik "wstrzymaj animacje" w nawigacji (`<button aria-pressed>`, stan w `localStorage`), który zatrzymuje cały ticker i spełnia 2.2.2 dla wszystkich kanw naraz; alternatywą są pętle do 5 s zatrzymujące się po jednym przebiegu. Przy `prefers-reduced-motion: reduce` strona pokazuje postery zamiast autoplay, wyłącza scrub i paralaksę, renderuje scenę 3D raz (effects.js już robi to dla kanw) i nasłuchuje `change`, by reagować na przełączenie ustawienia systemowego. Podglądy po hover powinny też startować na `:focus-visible` linku karty, rolki mieć natywne `controls`, a ciche dema krótki opis tekstowy przez `aria-describedby`; dekoracyjne `<video>` i `<canvas>` dostają `aria-hidden="true"`. Galerie kręcone kółkiem w `#projects` potrzebują ścieżki klawiaturowej, np. kropek jako przycisków.

## Conclusion

Najważniejsza zmiana perspektywy: droga do poziomu nagród dla tej strony nie prowadzi przez dodanie 3D i wideo, tylko przez zamianę zbioru niezależnych efektów w jeden język ruchu ze wspólnym zegarem, jednym akcentem kolorystycznym i jednym obiektem-podpisem. Naprawa integracji Lenis + ScrollTrigger jest tu nie tylko warunkiem technicznym, ale najtańszym krokiem o najwyższym zwrocie, bo prawdopodobnie usuwa długo nierozwiązany błąd reveal-i i jednocześnie odblokowuje scrubowaną kamerę 3D, CSS scroll-timelines i spójne pauzowanie wszystkiego jednym przyciskiem dla WCAG 2.2.2. Drugi nieoczywisty wniosek: skoro jury konsekwentnie ocenia dostępność najniżej, a portfolio elektroników praktycznie nie istnieją wśród zwycięzców, Piotr może konkurować nie skalą WebGL, tylko precyzją tematu (oscyloskop, antena SeeSky, prawdziwe PCB z KiCada) połączoną z wzorowym reduced motion i budżetem mobilnym, czyli dokładnie tym, czego większość zwycięzców nie dowozi.

Kolejność działań, która z tego wynika, to najpierw kopia zapasowa zgodnie z regułą z CLAUDE.md, potem poprawka tickera i usunięcie `scroll-behavior: smooth`, potem klipy wideo projektów w istniejących boksach i modal w miejsce lightboxa, a dopiero na końcu jeden leniwie ładowany model anteny. Taki porządek pozwala sprawdzać `/jury` i Lighthouse po każdym kroku i zatrzymać się w dowolnym momencie z działającą stroną. Otwarte pozostają: licencja pliku STEP Basys 3, wierność materiałów w natywnym eksporcie GLB z KiCada 9, faktyczne wydanie scroll-driven animations w Firefoksie 159 oraz to, czy CDN GitHub Pages kompresuje pliki `.glb`, co warto potwierdzić przed wdrożeniem.
