How I build with AI

I use Claude Code and Codex every day, and they write a good part of the code. Work from one model gets reviewed by another of similar strength from a different company: a fresh context helps, but a model trained differently also reasons differently and catches other mistakes. When something has to be right, I have a stronger model walk me through the whole file until I understand what it does and why. Everything runs through Codeg: it keeps my Claude Code, Codex and OpenCode subscriptions in one place, and a lead agent hands out tasks based on how capable and how fast each model is.

At a company the data matters most. Sensitive data stays inside a sandbox and, depending on how sensitive it is, does not go to OpenAI or any other model provider at all. Agents work on placeholder data with the same structure, and the real data goes into the real system in bulk only after the change has passed its tests.

Below is the workflow I would use on a team, where a mistake costs more.

  1. G1Research and plan

    Read-only agents study the problem: the existing codebase, its documentation and external solutions such as APIs and libraries. The problem is then decomposed into components, and the plan defines the modules, their interfaces and the files each component may modify. A human approves the plan before implementation begins.

    read-only agents + human
  2. G2Split into blocks

    The lead agent splits the plan into independent blocks with defined inputs and outputs. No two blocks edit the same file, so they run in parallel and merge without conflicts. A failed block is redone without touching the rest.

    lead agent
  3. G3Dispatch agents

    Each block gets its own coding agent, on its own branch, in a sandbox. The agent can run only the commands its task needs and sees only the files the plan lists for it. An agent that is confused or misled cannot reach beyond its block.

    coding agents
  4. G4Independent review

    A different model of similar strength reviews each diff in a fresh context, checks it against the plan and runs the tests. A failed block goes back to its agent with the review notes, and the loop repeats until the block passes.

    reviewer agent
  5. G5Merge and approval

    The change runs on placeholder data first, then on real data. It is merged only after a person approves it and can explain how it works. Larger changes get a backup first, so they can be rolled back. Problems users report afterwards go back to G1 as new requirements.

    human

Where it can go wrong

The agents are boxed in mainly because of prompt injection: a leak becomes possible when the same agent reads untrusted content, can reach private data and can send data out (the lethal trifecta). A model rates its own code too highly, so a different model reviews it, and one green test run is not enough (passk, not pass@1). Every new dependency is checked at its source, because models invent package names and attackers register them.

I haven't run agents in a company's production environment yet. Based on my own knowledge, drawing on Building effective agents, Claude Code best practices and the OWASP GenAI Security Project, I would propose a similar setup there.
